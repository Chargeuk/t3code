# Pipelines

## Overview

Adapt CodeInfo2's native Pipelines (called flows in its source) as executable, file-defined T3 automations. This plan owns the native Pipeline definition package, Pipeline-specific execution and SQLite history, the Pipeline portion of the automation UI, and focused proof. It consumes the shared file-backed Agent and Routine definitions/execution owned by [Agents and Routines](0000002-agents-and-routines.md); it consumes Repository Knowledge only for native re-ingestion steps, and Codebase Questions only when a Pipeline invokes that service. The product Linux runtime and Docker project-control capability belong to plan 0000002; this plan verifies its use and shares the integrated product-runtime proof rather than requiring a second runtime implementation.

Do not treat recommendations in the older `t3code-port-research-2026-11-08.md` report as accepted requirements; use current CodeInfo2 source/definitions and callers together with current T3 seams. For same-host CodeInfo2 work, keep CodeInfo2 agents, flows, and plan helpers on the host; run T3 `vp`, `node`, and `cargo` through `npm run container:exec -- <command>` from the T3 root, using existing `container:up`/`container:dev` as needed. Follow [repository container guidance](../AGENTS.md#dev-servers) and [Linux development container details](../docs/internals/devcontainer.md).

This is an implementation plan for the current parity baseline, not a request to implement now. The source baseline is CodeInfo2 `c90c52559` at `/home/dan/code/codeInfo2` and T3 `f69ad79ad9` at `/home/dan/code/t3code`. The CodeInfo2 flow schema and execution behavior were traced through the current schema, handlers, helpers, definitions, and callers. Paths below are source-backed navigation references with line ranges in link labels; they identify seams, not an instruction to modify every file. The CodeInfo2 checkout is a sibling, so its relative links begin `../../codeInfo2/`. T3 links from this directory begin `../`.

The verified native schema contains 18 step types (20 schema alternatives because `reingest` has three selectors). Preserve the definitions' supported observable behavior and actual control flow, not just prompts that describe it. Keep T3 as the owner of provider threads, orchestration events/effects, guarded RPC permissions, scheduling, and client state. Add only Pipeline-specific durable state needed to resume and inspect execution. Use the existing Scheduler for persisted due work. Scheduled Task success means dispatch succeeded, not that a provider turn completed; use the existing ThreadManagement wait/interrupt behavior when a step needs terminal thread outcomes.

The minimal proposed product asset root has one shared packaged layout:

```text
<native-assets>/
  t3_agents/<name>/{config.toml,description.md,system_prompt.txt,commands/*.json}
  pipelines/*.json
  codeinfo_markdown/**
  scripts/**
```

Project overrides are `<project>/t3_agents/` and `<project>/pipelines/*.json`; prompt overrides may be `<project>/pipelines/codeinfo_markdown/**`. A definition can explicitly name a repository Python path such as `pipelines/scripts/foo.py`; do not add a packaged-script precedence or override search policy. Packaged prompts and scripts live once at the shared native-assets root, not under `pipelines/`. Keep this support root independent from a configurable Pipeline catalog root. `CODEINFO_ROOT` may point to native-assets only in execution-scoped native T3 automation; never overwrite the host CodeInfo2 environment. Native Markdown lookup is working-project `pipelines/codeinfo_markdown`, definition-owner `pipelines/codeinfo_markdown`, packaged `native-assets/codeinfo_markdown`, then other configured native prompt roots, preserving missing-file fallback and selected invalid/unreadable-file errors. Do not resolve product prompts from the project's existing workflow `codeinfo_markdown/`. An explicitly named `decisionScript` resolves against the packaged harness/native-asset root; Python question/condition paths resolve in the worked project exactly as authored. No separate packaged-script override precedence or search policy is added. Keep the `command` discriminator and `commandName` for compatibility; user-facing definitions are Routines and use the shared message/re-ingest format, not arbitrary shell. Existing project `flows/`, `commands/`, `codeinfo_markdown/`, and `t3code_implement_story` remain unchanged.

The reference inventory currently describes 24 Pipeline definitions, 11 directly invoked Routine files, 189 Markdown files, and 49 support scripts, plus shared Agents. These counts and names aid navigation; they are not bulk-copy targets or mandatory completion totals. Adapt or reuse definitions required by accepted entrypoints and their complete actual transitive closure. Preserve accepted workflows; do not infer that any particular workflow can be deleted.

## Out of Scope

- Historical Mongo data, prior CodeInfo2 Pipeline runs, sessions, conversations or credentials; use fresh T3 state and re-ingest source material.
- Replacing native execution with prompt-only instructions; dropping a native type because its implementation is involved; adding unsupported shell/logical/review/Git/Docker step types; or adding a generic raw-shell Routine item.
- A new scheduler/workflow framework, Mongo layer, definition editor, duplicate history/catalog/provider runtime, Docker Engine abstraction, sandbox rewrite, or generic execution framework.
- New universal launch gates, approvals, receipts, preflights, freshness checks, allowlists, quotas, global worker caps, or handoff/control state. Existing scoped review requirements and T3 authorization/correctness remain as they are.
- Automatic target container/volume deletion or cancellation semantics that stop detached project containers. Docker lifecycle is explicit project work and uses the capability from plan 0000002.
- Kadshow/Jira integrations/defaults, the project-workflow folders `flows/`, `commands/`, `codeinfo_markdown/`, or `t3code_implement_story`, and changes to existing CodeInfo2 workflow definitions as a side effect.
- Making Knowledge or Questions a dependency for Pipelines that do not invoke ingestion or questions. Plans 0000001 and 0000003 remain the respective service owners.
- Copying CodeInfo2's entire runtime image, apt/pip bundle, unrelated OCR/PDF/Terraform/Rust/image tooling, or adding npm OpenCode as a substitute for the pinned `ocr` review binary.
- Windows/macOS/mobile/native packaging and proof. Scope is Linux web/server/shared.
