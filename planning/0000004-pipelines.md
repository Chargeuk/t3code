# Pipelines

## Overview

Adapt CodeInfo2's native Pipelines (called flows in its source) as executable, file-defined T3 automations. This plan owns the native Pipeline definition package, Pipeline-specific execution and SQLite history, the Pipeline portion of the automation UI, and focused proof. It consumes the shared file-backed Agent and Routine definitions/execution owned by [Agents and Routines](0000002-agents-and-routines.md); it consumes Repository Knowledge only for native re-ingestion steps, and Codebase Questions only when a Pipeline invokes that service. Plan 0000001 introduces the T3-root `docker-compose.yml` and persistent Chroma service named `chroma`. Plan 0000002 adds the base T3/provider product image and service to that same Compose, plus Docker project-control capability. Story 4 extends only the plan 0000002 image with review tools and helper assets actually invoked by its accepted definitions; it shares the integrated product-runtime proof rather than requiring a second runtime implementation.

Do not treat recommendations in the older `t3code-port-research-2026-11-08.md` report as accepted requirements; use current CodeInfo2 source/definitions and callers together with current T3 seams. For same-host CodeInfo2 work, edits and Git state share the host checkout; keep CodeInfo2 agents, flows, and plan helpers on the host. From the T3 root, run T3 tooling, checks, builds, and dependency installation inside the dedicated existing container through `npm run container:exec -- <command>`, using existing `container:up`/`container:dev` as needed. Future feature dependencies must be added through normal manifests/setup in that workflow; baseline/probe success does not establish that all future dependencies are installed. Do not create per-worker containers. Product-runtime requirements and proof remain separate. Follow [repository container guidance](../AGENTS.md#dev-servers) and [Linux development container details](../docs/internals/devcontainer.md).

This is an implementation plan for the current parity baseline, not a request to implement now. Scheduled Task success means dispatch succeeded, not that a provider turn completed; use the existing ThreadManagement wait/interrupt behavior when a step needs terminal thread outcomes.

Pipeline Agent slots associate reusable plan 0000002 Agent profiles (instructions/defaults/Routines) with ordinary native T3 threads/tasks and native ModelSelection. They do not create CodeInfo conversations or a parallel provider, identity, or conversation authority; one profile may instantiate multiple native threads. Any parent capable of native delegation may independently select any configured supported child provider instance/model/options accepted by existing target resolution. Explicit child choices override profile defaults; defaults do not impose role/provider pairs, and inherited parent values must not silently erase a role default. Preserve existing partial-target/options inheritance and clearing, authorization, project enablement, availability, and capability handling. Do not add a registry, pair table, same-provider restriction, catalog allowlist, or preflight. Provider-native subagent features remain distinct from app-owned cross-provider delegation. Non-thread Pipeline control steps need no artificial parent thread.

## Out of Scope

- Historical Mongo data, prior CodeInfo2 Pipeline runs, sessions, conversations or credentials; use fresh T3 state and re-ingest source material.
- Replacing native execution with prompt-only instructions; dropping a native type because its implementation is involved; adding unsupported shell/logical/review/Git/Docker step types; or adding a generic raw-shell Routine item.
- A new scheduler/workflow framework, Mongo layer, definition editor, duplicate history/catalog/provider runtime, Docker Engine abstraction, sandbox rewrite, or generic execution framework.
- A parallel provider/conversation authority or provider-pair registry, same-provider restriction, catalog allowlist, or preflight for child selection. Native T3 ModelSelection and target resolution remain authoritative.
- A standalone GitHub review/API helper port such as `githubReview.ts`, or duplicate GitHub authentication, routing, pagination, PR creation, activity/comment, or close-action engines. Existing T3 source-control and Pull Request services remain authoritative; Pipeline owns only execution-scoped PR association, feedback/handoff state, and its existing scoped recovery/outcome behavior.
- New universal launch gates, approvals, receipts, preflights, freshness checks, allowlists, quotas, global worker caps, or handoff/control state. Existing scoped review requirements and T3 authorization/correctness remain as they are.
- Automatic target container/volume deletion or cancellation semantics that stop detached project containers. Docker lifecycle is explicit project work and uses the capability from plan 0000002.
- Kadshow/Jira integrations/defaults, the project-workflow folders `flows/`, `commands/`, `codeinfo_markdown/`, or `t3code_implement_story`, and changes to existing CodeInfo2 workflow definitions as a side effect.
- Making Knowledge or Questions a dependency for Pipelines that do not invoke ingestion or questions. Plans 0000001 and 0000003 remain the respective service owners.
- Copying CodeInfo2's entire runtime image, apt/pip bundle, unrelated OCR/PDF/Terraform/Rust/image tooling, or adding npm OpenCode as a substitute for the pinned `ocr` review binary.
- Windows/macOS/mobile/native packaging and proof. Scope is Linux web/server/shared.
- Required live paid-provider/reviewer/GitHub credentials or network proof. Automated behavior uses existing deterministic native test seams; Story 1's real Knowledge/Chroma/SQLite proof with deterministic embedding fixtures and Story 2's product-runtime proof remain required; live LM Studio is optional only when explicitly requested.
