# Codebase Questions

## Overview

Deliver repository-scoped codebase questions as a T3 capability backed by Knowledge retrieval and the reusable Agent execution owned by sibling plans. The feature has one shared server-side question service for chat and MCP callers, a Knowledge-surface source selector, bounded research through ordinary T3 threads/provider tools, and source references opened in T3's existing file viewer. This is a work-ready plan, not an implementation or a migration of CodeInfo2 runtime data.

Do not treat recommendations in the older `t3code-port-research-2026-11-08.md` report as accepted requirements; use current CodeInfo2 source/definitions and callers together with current T3 seams. For same-host CodeInfo2 work, keep CodeInfo2 agents, flows, and plan helpers on the host; run T3 `vp`, `node`, and `cargo` through `npm run container:exec -- <command>` from the T3 root, using the existing dedicated container via `container:up`/`container:dev` as needed. Edits and Git state share the host checkout; future feature dependencies must be added through normal manifests/setup inside this workflow. Baseline or probe dependencies do not establish that all future feature dependencies are installed. Do not create per-worker containers. Follow [repository container guidance](../AGENTS.md#dev-servers) and [Linux development container details](../docs/internals/devcontainer.md).

The parity reference is CodeInfo2 `c90c52559`; the audited T3 baseline is `39c72e0b65`. Relevant reference sources include [`codebaseQuestion.ts`](../../codeInfo2/server/src/mcp2/tools/codebaseQuestion.ts) (contract and execution), [`systemContext.ts`](../../codeInfo2/common/src/systemContext.ts) (research protocol and repository selection), [`chat_search_agent/`](../../codeInfo2/codeinfo_agents/chat_search_agent/) (read-only leaf instructions), and [`lmstudio/tools.ts`](../../codeInfo2/server/src/lmstudio/tools.ts) (parent tools). Paths and cited source ranges below are navigation evidence, not instructions to modify every file.

Verified T3 seams include provider event persistence in [`ProviderEventIngestor.ts`](../apps/server/src/orchestration-v2/ProviderEventIngestor.ts), interruption in [`ProviderTurnControlService.ts`](../apps/server/src/orchestration-v2/ProviderTurnControlService.ts), persisted composer context in [`composerContext.ts`](../packages/contracts/src/composerContext.ts) and its provider projection in [`composerContextReferences.ts`](../packages/shared/src/composerContextReferences.ts), and environment-aware file links in [`ChatMarkdown.tsx`](../apps/web/src/components/ChatMarkdown.tsx) / [`MarkdownFileLink.tsx`](../apps/web/src/components/chat/MarkdownFileLink.tsx). `AssistantCitation` is for quoted chat text, not repository citations ([contract](../packages/contracts/src/assistantCitations.ts)). The generated route inventory currently has no Knowledge route ([`routeTree.gen.ts`](../apps/web/src/routeTree.gen.ts)); add the question entry to the Knowledge surface owned by plan 0000001 rather than duplicating that page.

CodeInfo2's MCP question input has no repository selector ([`codebaseQuestion.ts`](../../codeInfo2/server/src/mcp2/tools/codebaseQuestion.ts)); its shared prompt resolves named repositories, while retrieval tools resolve selectors and an unfiltered vector query may search globally ([`systemContext.ts`](../../codeInfo2/common/src/systemContext.ts), [`repositorySelector.ts`](../../codeInfo2/server/src/mcpCommon/repositorySelector.ts), [`toolService.ts`](../../codeInfo2/server/src/lmstudio/toolService.ts)). Therefore explicit selected source IDs and inheritance by omitted retrieval selectors are a small T3 binding required by the accepted selection UI. This preserves user scope; it is not a new filesystem security or allowlist framework.

CodeInfo2's protocol is model-facing instructions, not an enforced scheduler: start with 1–4 complementary vector queries; broad research uses 2–4 workers including a breadth assignment; later waves are conditional, with no extra vector searches in wave three. The only VectorSearch skip cases are an explicit user instruction, or applicable prior vector findings in the same conversation for the same question and current repository state. When validly skipping, preserve the prefix “I am skipping VectorSearch because [reason].” Disclose lookup failures; do not fabricate results or silently fall back. Preserve the source protocol's Questions-local instructions: 8 vector queries, 12 assignments, 4 active workers, 4 extra parent evidence calls; per worker 4 evidence calls, 200 lines/read, 10,000 characters of shell output, 50 AST symbols and 4,000 response characters; parent answers up to 8,000 characters. These are model-facing behavior, not hardcoded global enforcement. Adapt them through Agents; do not create a scheduler or global cap. Separate independent calls should launch before collection, settle through native T3 lifecycle, and retain assignment identity on follow-up ([protocol, lines 1–28](../../codeInfo2/common/src/systemContext.ts)). The leaf forbids edits, execution, delegation, vector searches and `code_info`, but is not an OS sandbox ([leaf prompt](../../codeInfo2/codeinfo_agents/chat_search_agent/system_prompt.txt)). Instruct the leaf not to recursively call research tools; do not add an MCP ACL/capability framework to enforce that instruction. Native T3 named-Agent tool names and task/thread identities replace CodeInfo2 MCP tool names, `functions.exec` examples, and conversation IDs. Preserve the reference MCP's final-answer filtering of thinking/vector summaries unless explicitly required otherwise ([`codebaseQuestion.ts`](../../codeInfo2/server/src/mcp2/tools/codebaseQuestion.ts)).

Ownership is split: plan 0000001 Knowledge owns canonical source IDs/paths, index/AST/embedding state, settings, lifecycle, retrieval, and Knowledge source UI; plan 0000002 Agents and Routines owns file-backed definitions/profiles, Agent execution, provider tools and provider support; this plan owns the question service, bounded question behavior, question UI entry and MCP surface; plan 0000004 Pipelines may call the shared question service but does not duplicate it. Implementation and proof workers must use this shared checkout. Creating or using Git worktrees is prohibited for this work; the existing T3 worktree feature remains unchanged. Agree shared contracts and assign one writer for shared contracts, RPC/server registration, migration registration, client-runtime state, navigation, and Settings. Proposed native definition layout is separate under `t3_agents/<name>/` (`config.toml`, `description.md`, `system_prompt.txt`, `commands/*.json`) and `pipelines/*.json`; these are proposed paths, not existing files. Existing `flows/`, `commands/`, `codeinfo_markdown/`, and `t3code_implement_story` remain project workflow files, unchanged. Keep the accepted scope and repository KISS constraints across all implementation and proof work; add no gates, approvals, receipts, preflights, allowlists, quotas or control machinery.

Use configured T3 provider instances and existing thread execution for questions; native LM Studio SDK embeddings remain required by Knowledge, while a new native LM Studio chat driver is not part of this plan. Initial chat/MCP question entry calls the Questions service, which resolves the binding and launches an ordinary T3 thread with `workspaceStrategy: { type: "root" }`, the selected provider/model, and typed Knowledge context. The ordinary thread is the parent; Questions supplies its trusted parent protocol. Subsequent ordinary chat follow-ups bypass the Questions service and inherit scope through serialized message dispatch/provider preparation. Named-Agent execution is only for the reusable `chat_search_agent` leaf profile, selected through the optional named-definition selector on existing `delegate_task`; the leaf receives the same source binding and never the parent protocol. This profile supplies instructions/defaults and applies to ordinary native T3 child threads/tasks; it is not a separate Questions provider, conversation, history, or scheduler runtime. T3 provider instances, native ModelSelection, configuration/secrets, threads/tasks/turns/cancellation/history, workspace/projects, toolkits/RPC, Scheduler, and UI remain their existing authorities; one profile may be applied to multiple native threads. Any parent capable of native delegation can choose any configured supported child provider instance/model/options accepted by existing target resolution, independently of the parent choice. Explicit child choices override profile defaults; defaults are not mandatory role/provider pairs, and inherited parent values must not erase a role default. Preserve existing partial-target/options inheritance and clearing, authorization, project enablement, availability, and capability handling. Codex/Copilot references below describe compatibility only, not exclusive research backends. Bind trusted profile tools at start/resume; MCP activation is provider-specific and must not assume hot reconfiguration for each source selection. Keep source scope in server-resolved message context. T3 has Codex and Copilot through existing paths ([built-in drivers](../apps/server/src/provider/builtInDrivers.ts), [ACP detection](../packages/provider-acp-registry/src/server/adapter.ts)); existing ACP supports Copilot MCP/model HTTP, continuation, and stop. ACP does not accept native System/Developer roles, so trusted server instructions use T3’s ACP preamble without claiming native role-priority parity or adding a Copilot SDK engine. Plan 0000002 owns generic named-definition preparation/launch and trusted-instruction plumbing, independent of Questions. This plan owns the Questions parent protocol and selection logic, while the generic `chat_search_agent` leaf definition remains owned by plan 0000002.

## Acceptance Criteria

- [ ] **Q-1 — Shared entry points:** Initial chat and MCP question entry invoke one question service and return associated thread/run identity, terminal status, actual provider/model, answer, and source references or explicit evidence limits. The service launches an ordinary T3 parent thread; MCP does not require an already-active provider parent. Ordinary chat follow-ups use native message intake and shared binding propagation/provider preparation, not a required Questions RPC for each message.
- [ ] **Q-2 — Scope:** The user-selected environment-local source IDs are resolved to canonical Knowledge IDs server-side and persisted as one typed Knowledge-source composer-context record, referenced from each question message using ordinary `t3-context` text so existing provider projection includes it. Omitted follow-up selections inherit the persisted binding; an explicit source selection replaces it. Omitted retrieval selectors inherit the binding; explicit selectors outside it cannot widen retrieval, and omission never means global retrieval. Use Knowledge's canonical IDs and paths, not a question catalog.
- [ ] **Q-3 — Research behavior:** Retain bounded vector-led discovery, complementary research when warranted, conditional waves, current-source verification, useful evidence reuse, precise citations, uncertainty, and research instructions/budgets from current CodeInfo2. Query/worker budgets are model-facing instructions, not unit-enforced gates. Independent results keep their originating logical assignment and child-thread association even if completion order reverses. A finished-child follow-up may retain the child thread while returning fresh native task/run IDs; steering may reuse an active run. Consume the actual IDs returned by `t3_thread_send` for wait, status, cancellation, and results; do not persist fixed task/run IDs as assignment identity. Leaf workers are instructed not to recursively call research tools and to behave read-only; no OS sandbox or MCP ACL is implied.
- [ ] **Q-4 — Providers and lifecycle:** Use configured T3 provider instances and preserve their existing provider behavior, native ModelSelection, profile/system-prompt/MCP compatibility, thread lifecycle, and actual provider/model identity. Any parent capable of native delegation may independently select any configured supported child provider instance/model/options accepted by existing target resolution; explicit child choices override profile defaults, defaults do not mandate role/provider pairs, and inherited parent values must not silently erase a role default. Preserve existing partial-target/options inheritance and clearing plus authorization, project enablement, availability, and capability handling. Provider-native subagent features and app-owned cross-provider delegation are distinct; add no registry, backend-pair table, catalog allowlist, or same-provider restriction. Do not silently substitute an explicitly requested provider or model. No new native LM Studio chat driver is required; Knowledge still requires native LM Studio SDK embeddings. Use T3 thread/event/SQLite/provider cancellation and failure lifecycle; preserve partial results and terminal status honestly. Keep secrets server-side through existing configuration.
- [ ] **Q-5 — Evidence and source navigation:** Use Knowledge vector/AST/source-location services. Chunk `lineCount` is not a source start line ([reference vector fields](../../codeInfo2/server/src/lmstudio/toolService.ts)); exact locations come from current source or reliable AST ranges ([AST records](../../codeInfo2/server/src/ast/toolService.ts)). Repository references navigate through the existing environment-aware Markdown/file panel, including remote environment paths; do not treat `AssistantCitation` as a repository citation.
- [ ] **Q-6 — Honest unavailable states:** Empty, stale, missing, or unavailable index/provider/source and worker failures produce a useful answer or partial result with limitations; no fabricated citations, automatic ingestion, freshness preflight, or new launch gate. Use normal schema migration lifecycle only if a schema change is needed. Fresh T3 state and re-ingestion replace historical CodeInfo2 data.
- [ ] **Q-7 — Minimality:** Implement the smallest requirement-complete reuse/minimal adaptation of CodeInfo2 behavior and T3 Knowledge, Agent/provider, SQLite, contract, RPC/MCP, and UI paths. No discretionary refactor/polish, unrelated repair, duplicate catalog/history/runtime/scheduler, new dependency/abstraction/helper/framework without an accepted requirement, verified gap, and reason reuse is insufficient. Add no gates, approvals, receipts, preflights, freshness requirements, allowlists, quotas, global worker caps, or handoff/control state. Retain existing authorization/correctness and required repository proof; project-specific review checks do not become launch gates.
- [ ] **Q-8 — Focused automated proof:** Existing Vitest/@effect/vitest/SQLite.layerMemory and browser component harnesses prove meaningful changed behavior at the lowest useful layer. Reuse plan 0000002’s positive heterogeneous native delegation and profile-target precedence tests for shared selection/default behavior. Questions-specific focused proof shows correct source context, named profile instructions, and actual selected native provider/task/thread identity on the shared path; it does not repeat unchanged native selection or lifecycle algorithms or require a real-provider matrix. Use deterministic provider/protocol fixtures through existing native seams for Questions behavior, alongside the actual Questions service and SQLite layer. Map concrete acceptance behaviors to owning tests: service scope, partial/unavailable results and shared caller semantics at the service layer; context draft-to-wire serialization, projection, and follow-up/reload at existing composer-context/projection tests; native settlement, stop and continuation in existing thread lifecycle tests. Use Deferred/events/Queue/TestClock/effect-worker drain, never sleeps, polling, timing deltas, retries, or per-test timeouts. Extend fitting existing tests; no duplicate transport mirrors, unchanged selection/lifecycle algorithms, type-only/static prompt-copy tests, mock mode/fake-provider product feature, auth bypass/endpoint fallback, exhaustive live-provider matrix, or new harness/framework. Consult [`evals/README.md`](../evals/README.md) and applicable eval guidance when model-facing text changes; retain affected local grader/unit checks.
