# Codebase Questions

## Overview

Deliver repository-scoped codebase questions as a T3 capability backed by Knowledge retrieval and the reusable Agent execution owned by sibling plans. The feature has one shared server-side question service for chat and MCP callers, a Knowledge-surface source selector, bounded research through ordinary T3 threads/provider tools, and source references opened in T3's existing file viewer. This is a work-ready plan, not an implementation or a migration of CodeInfo2 runtime data.

Do not treat recommendations in the older `t3code-port-research-2026-11-08.md` report as accepted requirements; use current CodeInfo2 source/definitions and callers together with current T3 seams. For same-host CodeInfo2 work, keep CodeInfo2 agents, flows, and plan helpers on the host; run T3 `vp`, `node`, and `cargo` through `npm run container:exec -- <command>` from the T3 root, using existing `container:up`/`container:dev` as needed. Follow [repository container guidance](../AGENTS.md#dev-servers) and [Linux development container details](../docs/internals/devcontainer.md).

The parity reference is CodeInfo2 `c90c52559`; the implementation target is T3 `f69ad79ad9`. Relevant reference sources include [`codebaseQuestion.ts`](../../codeInfo2/server/src/mcp2/tools/codebaseQuestion.ts) (contract and execution), [`systemContext.ts`](../../codeInfo2/common/src/systemContext.ts) (research protocol and repository selection), [`chat_search_agent/`](../../codeInfo2/codeinfo_agents/chat_search_agent/) (read-only leaf instructions), and [`lmstudio/tools.ts`](../../codeInfo2/server/src/lmstudio/tools.ts) (parent tools). Paths and cited source ranges below are navigation evidence, not instructions to modify every file.

Verified T3 seams include provider event persistence in [`ProviderEventIngestor.ts`](../apps/server/src/orchestration-v2/ProviderEventIngestor.ts), interruption in [`ProviderTurnControlService.ts`](../apps/server/src/orchestration-v2/ProviderTurnControlService.ts), persisted composer context in [`composerContext.ts`](../packages/contracts/src/composerContext.ts) and its provider projection in [`composerContextReferences.ts`](../packages/shared/src/composerContextReferences.ts), and environment-aware file links in [`ChatMarkdown.tsx`](../apps/web/src/components/ChatMarkdown.tsx) / [`MarkdownFileLink.tsx`](../apps/web/src/components/chat/MarkdownFileLink.tsx). `AssistantCitation` is for quoted chat text, not repository citations ([contract](../packages/contracts/src/assistantCitations.ts)). The generated route inventory currently has no Knowledge route ([`routeTree.gen.ts`](../apps/web/src/routeTree.gen.ts)); add the question entry to the Knowledge surface owned by plan 0000001 rather than duplicating that page.

CodeInfo2's MCP question input has no repository selector ([`codebaseQuestion.ts`](../../codeInfo2/server/src/mcp2/tools/codebaseQuestion.ts)); its shared prompt resolves named repositories, while retrieval tools resolve selectors and an unfiltered vector query may search globally ([`systemContext.ts`](../../codeInfo2/common/src/systemContext.ts), [`repositorySelector.ts`](../../codeInfo2/server/src/mcpCommon/repositorySelector.ts), [`toolService.ts`](../../codeInfo2/server/src/lmstudio/toolService.ts)). Therefore explicit selected source IDs and inheritance by omitted retrieval selectors are a small T3 binding required by the accepted selection UI. This preserves user scope; it is not a new filesystem security or allowlist framework.

CodeInfo2's protocol is model-facing instructions, not an enforced scheduler: start with 1–4 complementary vector queries; broad research uses 2–4 workers including a breadth assignment; later waves are conditional, with no extra vector searches in wave three. The only VectorSearch skip cases are an explicit user instruction, or applicable prior vector findings in the same conversation for the same question and current repository state. When validly skipping, preserve the prefix “I am skipping VectorSearch because [reason].” Disclose lookup failures; do not fabricate results or silently fall back. It defines service-local budgets (8 vector queries, 12 assignments, 4 concurrent workers, 4 extra parent evidence calls; per worker 4 evidence calls, 200 lines/read, bounded shell output (10,000 characters), 50 AST symbols and 4,000 worker response characters; parent answers are limited to 8,000 characters), separate independent calls launched before collection, settled results, and identity-preserving follow-ups ([protocol, lines 1–28](../../codeInfo2/common/src/systemContext.ts)). Adapt these instructions through Agents; do not create a scheduler or global cap. The leaf forbids edits, execution, delegation, vector searches and `code_info`, but is not an OS sandbox ([leaf prompt](../../codeInfo2/codeinfo_agents/chat_search_agent/system_prompt.txt)). Preserve the reference MCP's final-answer filtering of thinking/vector summaries unless explicitly required otherwise ([`codebaseQuestion.ts`](../../codeInfo2/server/src/mcp2/tools/codebaseQuestion.ts)).

Ownership is split: plan 0000001 Knowledge owns canonical source IDs/paths, index/AST/embedding state, settings, lifecycle, retrieval, and Knowledge source UI; plan 0000002 Agents and Routines owns file-backed definitions/profiles, Agent execution, provider tools and provider support; this plan owns the question service, bounded question behavior, question UI entry and MCP surface; plan 0000004 Pipelines may call the shared question service but does not duplicate it. Agree shared contracts and assign one writer for shared contracts, RPC/server registration, migration registration, client-runtime state, navigation, and Settings. Proposed native definition layout is separate under `t3_agents/<name>/` (`config.toml`, `description.md`, `system_prompt.txt`, `commands/*.json`) and `pipelines/*.json`; these are proposed paths, not existing files. Existing `flows/`, `commands/`, `codeinfo_markdown/`, and `t3code_implement_story` remain project workflow files, unchanged.

Use configured T3 provider instances and existing Agent/thread execution for questions; native LM Studio SDK embeddings remain required by Knowledge, while a new native LM Studio chat driver is not part of this plan. T3 has Codex and Copilot through existing paths ([built-in drivers](../apps/server/src/provider/builtInDrivers.ts), [ACP detection](../packages/provider-acp-registry/src/server/adapter.ts)); existing ACP supports Copilot MCP/model HTTP, continuation, and stop. ACP does not accept native System/Developer roles, so trusted server instructions use T3’s ACP preamble without claiming native role-priority parity or adding a Copilot SDK engine. Plan 0000002 owns named-Agent execution through configured T3 providers, not a new LM Studio chat driver. The Agents owner selects the correct parent and leaf system prompts; do not port CodeInfo2’s bug that ignored the Agent system prompt. This plan defines the dependency and contract only.

## Acceptance Criteria

- [ ] **Q-1 — Shared entry points:** Chat and MCP invoke one question service and return associated thread/run identity, terminal status, actual provider/model, answer, and source references or explicit evidence limits. MCP calls establish or reuse an ordinary question thread through the Agent service; they do not require an already-active provider parent.
- [ ] **Q-2 — Scope:** The user-selected environment-local source IDs are persisted with the existing composer/message context and flow through discovery, retrieval, worker assignments, follow-ups, and answer evidence. Omitted retrieval selectors inherit the binding; explicit selectors outside it cannot widen retrieval. Use Knowledge's canonical IDs and paths, not a question catalog.
- [ ] **Q-3 — Research behavior:** Retain bounded vector-led discovery, complementary research when warranted, conditional waves, current-source verification, useful evidence reuse, precise citations, uncertainty, and service-local instructions/budgets from current CodeInfo2. Independent results keep their originating assignment identity; follow-ups resume only the matching assignment. Leaf workers cannot recursively call research tools and are instructed read-only; no OS sandbox is implied.
- [ ] **Q-4 — Providers and lifecycle:** Use configured T3 provider instances and preserve their existing provider behavior, profile/system-prompt/MCP compatibility, thread lifecycle, and actual provider/model identity. Do not silently substitute an explicitly requested provider or model. No new native LM Studio chat driver is required; Knowledge still requires native LM Studio SDK embeddings. Use T3 thread/event/SQLite/provider cancellation and failure lifecycle; preserve partial results and terminal status honestly. Keep secrets server-side through existing configuration.
- [ ] **Q-5 — Evidence and source navigation:** Use Knowledge vector/AST/source-location services. Chunk `lineCount` is not a source start line ([reference vector fields](../../codeInfo2/server/src/lmstudio/toolService.ts)); exact locations come from current source or reliable AST ranges ([AST records](../../codeInfo2/server/src/ast/toolService.ts)). Repository references navigate through the existing environment-aware Markdown/file panel, including remote environment paths; do not treat `AssistantCitation` as a repository citation.
- [ ] **Q-6 — Honest unavailable states:** Empty, stale, missing, or unavailable index/provider/source and worker failures produce a useful answer or partial result with limitations; no fabricated citations, automatic ingestion, freshness preflight, or new launch gate. Use normal schema migration lifecycle only if a schema change is needed. Fresh T3 state and re-ingestion replace historical CodeInfo2 data.
- [ ] **Q-7 — Minimality:** Implement the smallest requirement-complete reuse/minimal adaptation of CodeInfo2 behavior and T3 Knowledge, Agent/provider, SQLite, contract, RPC/MCP, and UI paths. No discretionary refactor/polish, unrelated repair, duplicate catalog/history/runtime/scheduler, new dependency/abstraction/helper/framework without an accepted requirement, verified gap, and reason reuse is insufficient. Add no gates, approvals, receipts, preflights, freshness requirements, allowlists, quotas, global worker caps, or handoff/control state. Retain existing authorization/correctness and required repository proof; project-specific review checks do not become launch gates.
- [ ] **Q-8 — Focused automated proof:** Existing Vitest/@effect/vitest/SQLite.layerMemory and browser component harnesses prove meaningful changed behavior at the lowest useful layer. Cover two-fixture scope, reverse-order worker association, failure/partial output, cancellation/no post-cancel dispatch, missing/empty/stale source behavior, citation navigation, follow-up/reload persistence, and shared chat/MCP service behavior. Use Deferred/events/Queue/TestClock/effect-worker drain, never sleeps, polling, timing deltas, retries, or per-test timeouts. Extend fitting existing tests; no duplicate transport mirrors, type-only/static prompt-copy tests, or new harness/framework. When model-facing instructions/MCP schemas/descriptions/results change, follow [`evals/README.md`](../evals/README.md) and applicable eval README, including relevant cases while iterating and one full applicable eval run per changed model before merge. Do not run unrelated repository eval suites or invent eval infrastructure.
- [ ] **Q-9 — Real client and external proof:** One integrated real-web pass occurs once after integration, using the existing [`test-t3-app` workflow](../.agents/skills/test-t3-app/SKILL.md), isolated state, existing Playwright and a dedicated tab. Verify source selection, question, source navigation, follow-up/reload and cancellation. Replay establishes observed UI only, not backend logic/provider tools. Run provider proof only for the actual configured provider(s) used by the accepted path; missing configuration leaves the relevant proof open with the exact missing item. Do not require a fixed three-engine matrix or claim unverified endpoint/model compatibility. Linux product deployment and explicit disposable target-stack start/stop proof is owned by plan 0000002 and reused by plan 0000004/integration; it is not repeated as a Questions-specific proof. No mobile/native or other OS proof.
- [ ] **Q-10 — Later integration proof:** Before a later push, run `npm run container:exec -- vp run check:changed`. This is an integration/push check, not a per-step gate; retain successful applicable proof unless a material change invalidates it.

## Out of Scope

- Knowledge source catalogs, ingestion/index/AST/embedding lifecycle, Chroma access/deployment, and canonical source metadata; owned by plan 0000001.
- Generic Agent/Routine definitions, provider profile/settings catalog, and provider execution infrastructure; owned by plan 0000002. A new native LM Studio chat driver is not required by this plan.
- Pipeline executor/history/UI, except calling the shared question service when a Pipeline explicitly invokes Questions.
- A separate research engine, scheduler, state machine, question history/catalog, Chroma client, provider runtime, or generic search product.
- Historical Mongo/session/conversation/run/credential migration. Start with fresh T3 state and re-ingest sources. Ordinary T3 schema migrations remain allowed.
- New security sandbox, filesystem allowlist, worker quotas/global caps, approvals, receipts, gates, freshness checks, or automatic ingestion.
- Kadshow/Jira generic defaults; changes to existing `flows/`, `commands/`, `codeinfo_markdown/`, or `t3code_implement_story` project workflow.
- Linux-external OS support, mobile, native packaging, and mobile/native verification.
- Discretionary refactors, unrelated repairs, speculative dependencies, and unconfigured-provider claims.

## Suggested Implementation

### 1. Agree source scope and shared service contracts

Dependencies: plan 0000001 source/retrieval contracts; plan 0000002 Agent execution and provider contracts. Questions owns its domain service and coordinates a single writer for shared transport/contracts/navigation seams.

- [ ] Define a minimal question request containing question text, explicit environment-local source IDs, destination project/thread context, and existing provider/model selection or Agent defaults. Define result fields for thread/run identity, terminal/partial status, actual provider/model, answer, and source references/evidence limitations. Reuse T3 identities; add no receipt/history store.
- [ ] Agree Knowledge service calls for canonical source resolution, scoped vector retrieval, AST/source ranges, runtime paths and ordinary unavailable results. Questions must not access Chroma or own source records. Relevant reference evidence: selector resolution in [CodeInfo2 `repositorySelector.ts`](../../codeInfo2/server/src/mcpCommon/repositorySelector.ts) and T3 provider/event lifecycle in [`ProviderEventIngestor.ts`](../apps/server/src/orchestration-v2/ProviderEventIngestor.ts).
- [ ] Agree Agents service calls to start/continue the named research Agent with trusted profile/instructions, bound source context, cancellation and terminal results. Assignments retain separate T3 thread/run identity; a follow-up uses only its own returned identity. Adapt the reference `run_agent_instruction` concept to T3's actual MCP/provider service rather than copying that API name or invoking `delegate_task` as an external entry point ([T3 delegation constraints](../apps/server/src/mcp/OrchestratorMcpService.ts)).
- [ ] Map the existing RPC permission, MCP tool-access, toolkit and environment authorization paths for the new entry point. Preserve those checks; do not create a permission framework. Keep transport handlers thin and invoke the shared service.
- [ ] Proof: review contracts against actual Knowledge and Agent callers before implementation; no standalone contract mirror tests where type/schema checks suffice.

### 2. Implement bounded, scope-preserving question service

Dependencies: agreed contracts and services from section 1; Knowledge retrieval and Agents execution.

- [ ] Add the question domain Effect service (proposed filename `apps/server/src/codebase-questions/CodebaseQuestionService.ts`) and a focused companion test (proposed `CodebaseQuestionService.test.ts`), following existing service/effect conventions. It binds the explicit source set to the existing composer/message context; verify provider projection includes the referenced context record ([contract](../packages/contracts/src/composerContext.ts), [projection](../packages/shared/src/composerContextReferences.ts)).
- [ ] Implement scope inheritance at the service/tool boundary: every omitted selector uses the bound IDs; an explicit outside selector is rejected or yields the established unavailable result without broadening. Test two fixtures with overlapping terms to show unrelated evidence never enters discovery, workers, or answer references.
- [ ] Adapt the current CodeInfo2 research protocol as instructions, not a scheduler: 1–4 initial complementary vector queries; 2–4 workers for broad questions including breadth coverage; conditional later waves and no new vectors in wave three; preserve the protocol's service-local budgets and separate-call launch-before-collection behavior. VectorSearch may be skipped only on explicit user instruction or applicable prior vector findings in the same conversation for the same question and current repository state; state “I am skipping VectorSearch because [reason].” for a valid skip. Disclose lookup failures without fabricated findings or hidden fallback. Do not add extra vectors/workers or a global cap beyond the reference instructions.
- [ ] Keep all independently dispatched work associated by its originating assignment identity even if completion order reverses; settle all launched calls, preserve successful evidence when one worker fails, and report partial status. Follow-up work reuses only its own task/thread identity.
- [ ] Use the dedicated read-only leaf definition owned/adapted by Agents, with scope/context passed through existing provider tools and no recursive research call. This is instruction-level read-only behavior, not an OS sandbox. Preserve native provider cancellation and ordinary error handling; after cancellation do not dispatch subsequent work, and let owned calls settle through T3 lifecycle.
- [ ] Verify current source before asserting exact line citations. Vector chunk length is not a source line; rely on Knowledge AST ranges or current file reads. Stale/empty/missing source produces qualified evidence or an honest limitation, never hidden reingestion/freshness gating.
- [ ] Preserve CodeInfo2's answer-segment filtering where it excludes internal thinking/vector summaries from the final MCP response; do not expose internal research artifacts unless required by the product contract.
- [ ] Focused service proof: scope across discovery and worker calls; reverse-order completion; one worker failure with retained successful evidence; cancellation before/during work and no later dispatch; empty/stale/missing source; source range correctness; partial/final result association and follow-up identity. Use deterministic Deferred/event/Queue/TestClock/effect-worker drain and SQLite.layerMemory where persistence is involved.
